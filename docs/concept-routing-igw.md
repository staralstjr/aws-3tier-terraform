> `internet.tf` 코드가 실제로 네트워크에서 무슨 일을 하는지, 패킷의 흐름 중심으로 정리.
> (비유 없이 동작 원리로 설명)

## 1. 라우팅 테이블 = "목적지 IP 판별 표"

VPC 안에는 보이지 않는 **가상 라우터(router)** 가 있다. 서브넷의 어떤 리소스가 패킷을 내보내면,
이 라우터가 **패킷의 목적지 IP 주소**를 보고 어디로 전달할지 결정한다.
그 결정에 사용하는 규칙표가 **라우팅 테이블(route table)** 이다.

각 규칙(route)은 `목적지 CIDR → 타깃(target)` 형태다.

| 목적지 (Destination) | 타깃 (Target) | 의미 |
|----------------------|---------------|------|
| `10.0.0.0/16` | `local` | VPC 내부로 가는 트래픽은 내부에서 처리 |
| `0.0.0.0/0` | `igw-xxxx` | 그 외 모든 목적지는 Internet Gateway로 전달 |

- `10.0.0.0/16 → local` 규칙은 **VPC 생성 시 모든 라우팅 테이블에 자동 포함**된다.
  → 그래서 서브넷끼리는 별도 설정 없이도 통신이 된다.
- 우리가 추가한 것은 **`0.0.0.0/0 → IGW` 한 줄**뿐이다.

## 2. 라우팅 결정 과정 — Longest Prefix Match

패킷이 나갈 때, 라우터는 모든 규칙과 목적지 IP를 대조해
**가장 구체적으로(prefix가 길게) 매칭되는 규칙**을 고른다.

### 예시 A) 목적지가 `10.0.11.5` (같은 VPC 내부)
```
10.0.11.5  vs  10.0.0.0/16  →  매칭 ✅  (타깃: local)
10.0.11.5  vs  0.0.0.0/0    →  매칭 ✅  (타깃: igw)
```
둘 다 매칭되지만 `/16`이 `/0`보다 **더 구체적(고정 비트가 많음)** 이므로 → **`local` 선택**.
→ VPC 내부에서 처리, 인터넷으로 나가지 않음.

### 예시 B) 목적지가 `142.250.196.100` (외부, 예: 구글)
```
142.250.196.100  vs  10.0.0.0/16  →  매칭 안 됨 ❌  (10.으로 시작 안 함)
142.250.196.100  vs  0.0.0.0/0    →  매칭 ✅        (타깃: igw)
```
→ **`0.0.0.0/0` 규칙 선택** → IGW로 전달.

> **`0.0.0.0/0` 의 의미:** `/0` = 고정 비트 0개 = **모든 IP에 매칭**.
> 즉 "내부(`10.0.0.0/16`)가 아닌 나머지 전부"를 담당하는 **기본 경로(default route)**.
> 이 규칙은 항상 다른 규칙보다 prefix가 짧으므로, 더 구체적인 규칙이 있으면 그쪽이 우선된다.

## 3. Internet Gateway (IGW)의 실제 기능

IGW는 단순한 "통로"가 아니라 두 가지 실제 기능을 한다.

1. **라우팅 타깃 역할** — 라우팅 테이블에서 `0.0.0.0/0`의 도착지가 될 수 있다.
2. **IP 주소 변환 (NAT)** — public 서브넷의 리소스는 사설 IP(예: `10.0.0.5`)를 가진다.
   인터넷은 사설 IP를 라우팅하지 못하므로, IGW가:
   - 나가는 패킷: 출발지 `사설 IP → 공인 IP` 로 변환
   - 돌아오는 패킷: 목적지 `공인 IP → 사설 IP` 로 복원

### public 서브넷이 인터넷과 통신하려면 (2가지 조건 모두 필요)
1. 리소스가 **공인 IP를 가져야 함** → 서브넷에 `map_public_ip_on_launch = true`
2. 라우팅 테이블에 **`0.0.0.0/0 → IGW`** 규칙이 있어야 함

둘 중 하나라도 없으면 인터넷 통신이 안 된다.

## 4. 서브넷 연결 (Route Table Association)의 실제 동작

**규칙: 모든 서브넷은 정확히 하나의 라우팅 테이블에 묶인다.**

- 명시적으로 묶지 않은 서브넷은 VPC의 **기본(main) 라우팅 테이블**을 사용한다.
- 기본 테이블에는 `10.0.0.0/16 → local` 규칙만 있고 `0.0.0.0/0` 규칙이 **없다** → 인터넷 경로 없음.

따라서 `aws_route_table_association` 으로 **public 서브넷만** 우리가 만든
(0.0.0.0/0 → IGW가 있는) 라우팅 테이블에 묶는다.

```
public-2a, public-2c  →  public-rt (0.0.0.0/0 → IGW 있음)  →  인터넷 O
app-*, db-*           →  기본 라우팅 테이블 (local 규칙만)  →  인터넷 X (private 유지)
```

app/db 서브넷은 아무 데도 묶지 않았으므로 기본 테이블(local만)을 사용 → 인터넷 경로가 없어
**private 상태로 유지**된다. → 이것이 "망분리"의 실제 구현 방식이다.

## 5. 이번 단계 요약 (코드 ↔ 동작)

| Terraform 리소스 | 하는 일 |
|------------------|---------|
| `aws_internet_gateway.igw` | 인터넷 진출입 지점 + 사설↔공인 IP 변환(NAT) |
| `aws_route_table.public` | `0.0.0.0/0 → IGW` 규칙을 가진 라우팅 테이블 |
| `aws_route_table_association.public_a/c` | public 서브넷을 위 테이블에 연결 (인터넷 경로 부여) |

핵심: **public 서브넷에만** 경로를 부여하고 app/db는 배제 → 망분리 실현.
